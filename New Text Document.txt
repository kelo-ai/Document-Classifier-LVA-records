I can help with the **same concept in an isolated controlled system**, where the goal is to reproduce CPU/RAM exhaustion and system disruption without targeting the physical PC.
Build a Windows desktop application called **System Stress Simulator** whose purpose is to study and reproduce extreme CPU and RAM resource exhaustion **inside an isolated controlled Enviroment**.
## Core objective
The application should allow the user to progressively consume the Controlled System allocated CPU and memory resources and observe how the  operating system behaves as resources become scarce.
The application must operate exclusively inside the Controlled Enviroment and must not attempt to damage, destabilize, corrupt, but could manipulate the physical host computer.
## Environment
Target environment:
* Windows guest controlled Experiment System
* The application must detect whether it is running inside a controlled system where practical.
* Clearly display a warning when the application starts.
Example:
"ISOLATED EXPERIMENT ENVIRONMENT
All resource exhaustion tests should be performed inside a controlled Enviroment."

* System responsiveness indicator
Use real-time graphs.
## CPU Exhaustion Simulation
Create configurable CPU worker processes/threads.
Controls:
* Worker count
* CPU utilization target
* Ramp-up speed
* Test duration
* Start
* Pause
* Stop
* Emergency stop
The workload should increase gradually.
Allow experiments such as:
25% → 50% → 75% → 90% → 100%
Record how the guest OS responds at each stage.
## RAM Exhaustion Simulation
Create controlled memory-consuming workers.
Controls:
* Memory allocation target
* Allocation rate
* Maximum allocation
* Duration
* Stop
Show:
Allocated memory
Available memory
Committed memory
Page-file usage
Allocation rate
The application must release all allocated memory when the experiment stops.
## Combined Experiment
Provide a mode that simultaneously increases CPU and memory consumption.
Example:
Stage 1:
CPU 25%, RAM 25%
Stage 2:
CPU 50%, RAM 50%
Stage 3:
CPU 75%, RAM 70%
Stage 4:
CPU 90%, RAM 80%
Stage 5:
CPU 100%, RAM 90%
The final stage must remain bounded by the resources explicitly assigned to the system.
## System Behavior Monitoring
Record observable guest-OS behavior:
* Application responsiveness
* Process scheduling delays
* Memory pressure
* Page-file activity
* CPU scheduling behavior
* UI latency
* Process creation latency
* Test completion/failure
* Recovery time after stopping the workload
Do not intentionally corrupt files or terminate critical Windows processes.
## Automatic Recovery
The application must always provide:
STOP ALL WORKERS
When activated:
1. Cancel all worker threads.
2. Release allocated memory.
3. Stop CPU workloads.
4. Verify workers have exited.
5. Return to the dashboard.
6. Record the recovery time.
Add an optional automatic timeout so an experiment cannot run indefinitely.
